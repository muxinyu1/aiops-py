# 图 7:反馈环密度与命中结果的关系(量化分析图)

## 这张图要表达什么

"请求后核对日志"(反馈环)的行为密度与运行结果正相关:命中运行的反馈环密度普遍更高,失败运行的典型特征是反馈环稀疏+盲目重发。为"偏差反馈是方法核心组件"提供统计证据。

## 环的定义(画图口径,需在图注说明)

**反馈环 = 一次 send_http 调用后的 2 步内出现 read_logs。** 反馈环密度 = 反馈环数 / send_http 数。

## 建议画法

**方案 A(推荐):散点图,x=反馈环密度,y=总调用数(对数),形状/颜色=命中/失败**
- 命中点绿色圆,失败点红色叉
- 可观察到:高预算 FAIL 的运行集中在"低密度+高调用数"区域(盲目重发特征);高密度(>0.4)区域以 PASS 为主
- 注意:该图相关性的解释要诚实——存在低密度 PASS(单跳任务无需反复核对)与一个高密度 FAIL(0.35,预算耗尽于别的死胡同),图注要说明密度是必要非充分条件

**方案 B:成对比较条形图(更保守,推荐给中期)**
只对比"同一 sink 多次运行"的组(menu_root ×3、menu_route_name ×2、wf_inst_var ×2、wf_listener_end ×3、wf_inst_orphan ×3),每组内标 FAIL/PASS 的反馈环密度。同任务同提示下差异更可信:
- menu_root: v1-FAIL 0.60 / v2-FAIL 0.05 / v3-PASS 0.50 (v2 盲发 21 请求)
- wf_inst_var: v1-FAIL 0.04 / v2-PASS 0.60
- wf_listener_end: clean-FAIL 0.35 / v1-PASS 0.38 / v3-PASS 0.60
- wf_inst_orphan: v1-FAIL 0.04 / v2-PASS 0.39 / v3-FAIL 0.10
- menu_route_name: v1-FAIL 0.14 / v2-PASS 0.33

方案 B 消除了"不同 sink 难度不同"的混杂变量,统计上更干净。

## 混杂因素说明(图注必须写)

1. 单跳简单任务(pig_file)天然低环数即命中——密度低不代表会失败;
2. 某些 PASS 运行靠 send_http 响应中的业务码(code 字段)即可判断分支,不依赖 read_logs;
3. 反馈还有其他通道(query_db 验证落库、HTTP 响应),read_logs 只是其一。
因此图的主题是"**反馈环密度与成功存在正相关倾向,FAIL 运行普遍呈低密度+高重发特征**",不做强因果声明。
