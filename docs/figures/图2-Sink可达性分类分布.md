# 图 2:Sink 黑盒可达性分类分布(核心数据图)

## 这张图要表达什么

黑盒 fuzz 在日志注入场景存在**结构性盲区**:2230 个 sink 中仅 196 个(占可达的 15.3%)可被黑盒 fuzz 触达,84.7% 的可达注入点需要前置状态构造——这是本方法存在的理由。

## 数据(已从 data/sink_llm_classify.json 统计核实)

**层级漏斗:**

| 层级 | 数量 |
|---|---|
| 全量提取 sink | 2230 |
| HTTP 不可达(定时任务/框架内部) | 937 |
| HTTP 可达 | 1277 |
| └ 黑盒可 fuzz(对照池) | 196 |
| └ 黑盒不可 fuzz(目标池) | 1081 |

**目标池 1081 个按不可达原因分解:**

| 原因 | 数量 | 占可达 1277 比例 |
|---|---|---|
| exception_path 依赖内部异常 | 405 | 31.7% |
| db_state 依赖数据库状态 | 225 | 17.6% |
| remote_service 依赖下游服务 | 181 | 14.2% |
| printed_value_not_request 打印值不可控 | 108 | 8.5% |
| internal_state 依赖配置开关 | 107 | 8.4% |
| cache_state 依赖缓存状态 | 55 | 4.3% |

## 建议画法

**方案 A(推荐):漏斗图 + 堆叠条形图组合**
- 左半:漏斗 2230 → 1277 → (196 | 1081) 两叉
- 右半:1081 横向堆叠条形按 6 类原因着色,每段标注数量与百分比

**方案 B:桑基图(Sankey)**
节点:全部 sink → HTTP可达/不可达 → 6 类原因。流向宽度按数量。视觉冲击强,但 6 个末端节点标签容易挤,建议横向大图。

**方案 C:双饼图**
左饼:可达/不可达;右饼:可达中可 fuzz/不可 fuzz。简单但不显示 6 类原因分解,信息量偏弱。

## 标注建议

在 1081 的堆叠段旁边加括号注释每类的"应对策略",呼应后续计划:
- exception_path → 畸形输入构造(下一步工作)
- db_state → Agent 状态构造(已验证 ✅)
- remote_service → mock 下游(下一步)
- cache_state → Redis 状态构造(pig 验证码已示范)
