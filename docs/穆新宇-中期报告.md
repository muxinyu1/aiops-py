## 一、课题调整说明

开题阶段的课题"基于大模型的 Web SQL 注入漏洞验证方法研究"以 SQL 注入为对象，研究 LLM 语义驱动的灰盒 fuzz：静态代码切片提供上下文，LLM 语义变异生成 Payload，执行流偏差反馈制导变异方向，带外 Oracle 确认漏洞。

中期阶段调整研究目标，主要基于两点考虑：

**其一，研究对象由"SQL 注入漏洞"扩展为"遥测数据注入"这一新兴威胁。** 随着 AIOps（智能运维）的兴起，LLM 驱动的运维 Agent 会读取系统遥测数据（日志、指标、追踪）进行根因分析并自动执行修复操作。USENIX Security 2026 的工作"When AIOps Become AI Oops"首次揭示：攻击者可以通过应用的公开 HTTP 接口构造恶意请求，使包含攻击载荷的内容被写入系统日志；当 AIOps Agent 后续读取这些日志时，会被注入的提示词误导，执行降级软件、添加恶意软件源等危害系统安全的操作。该工作的攻击工具 AIOpsDoom 采用黑盒 fuzz 方式枚举所有 HTTP 端点盲目注入，本质上依赖"碰运气"式触发。与之相比，我们的实验对象（多个真实开源微服务系统）中存在大量"用户输入只有在特定数据库状态下才会进入日志"的注入点，这类点黑盒 fuzz 结构上无法触达，需要先通过多步业务操作把系统状态推送到满足日志分支的条件——这正是 LLM Agent 语义推理能力的用武之地。

**其二，原开题的技术路线在新的研究对象下有更清晰的落点。** 原方案的核心组件——静态分析提取 sink、LLM 驱动 payload 生成、执行路径跟踪、执行偏差反馈——在新课题中全部保留并落地为"白盒定位日志 sink → LLM Agent 多步骤利用"的两阶段方案（详见研究方案）。相比 SQL 注入场景，日志 sink 的特殊性在于：sink 不是固定 API（`Statement.execute()` 之类），而是由项目实现方式决定的任意日志打印语句，这使静态 sink 定位本身成为需要研究的问题；同时日志注入的验证天然是确定性的（日志文件中检查攻击标记），无需带外 Oracle，验证闭环更干净。

调整后课题名称为：**基于大语言模型智能体的 Web 应用日志注入漏洞多步骤利用方法研究**。

## 二、课题研究内容

### 2.1 研究范围

本课题研究面向 Java 微服务 Web 应用的日志注入漏洞自动化利用技术。研究对象分为两个层面：

**静态层面是目标应用的源码与数据库模式。** 从真实开源微服务项目源码中提取日志打印语句作为候选 sink（按语义分类：直接日志调用、全局异常处理器、AOP 切面等），并结合调用图与 MyBatis ORM 映射推导"哪些 HTTP API 会读写哪些数据库表"。

**动态层面是可部署运行的微服务系统与其运行时状态。** 包括应用容器、MySQL、Redis 等中间件，以及这些组件中的业务数据状态（数据库表内容、缓存键值、用户账号状态等）。本课题的核心观察是：日志打印语句的可达性往往由运行时数据状态决定——例如"当且仅当数据库中存在某条与请求参数冲突的记录时，冲突日志分支才会执行"。

本课题假设攻击者具备目标系统的白盒源码访问权限（模拟供应链场景或内部攻击者，同时这也是发现防御盲区所需的前提），可以部署并观察目标系统，但**不拥有数据库的直接写权限**——所有对系统状态的修改必须通过应用的业务 API 完成。这一约束是本方法区别于既有工作（如直接 INSERT 种子数据）的关键设定，它保证了"多步骤利用"是攻击者在真实场景中真正可以复现的。本课题不考虑拒绝服务、侧信道等攻击类型，仅关注通过 HTTP 请求触发的日志注入路径。

### 2.2 研究问题

本课题围绕"如何让 LLM Agent 自主完成从 sink 定位到多步骤攻击触发的全流程"这一中心，需要解决三个核心研究问题：

**研究问题一：如何系统化地定位日志 sink 并刻画其触发条件？** 日志打印语句在真实项目中数量庞大（我们在 20 余个开源微服务项目中共提取 2230 条），且是否构成安全威胁需要语义判断（哪些日志的参数是用户可控的、哪些日志会被 AIOps Agent 读取）。需要一种自动化的 sink 提取与分类方法，输出每个 sink 的精确位置、日志模板、参数表达式，并判定其"黑盒可 fuzz 性"——即纯随机 fuzz 是否可能触发，从而将无法黑盒触达的 sink 筛选出来作为 LLM Agent 的目标池。

**研究问题二：如何让 LLM Agent 从 sink 的源码语义推理出完整的数据库状态前置条件与对应的 API 序列？** 这是本课题最核心的问题。典型场景是：sink 的日志分支要求"数据库中存在 path 与请求参数相同的菜单记录"——纯黑盒测试不知道这一条件，而知道条件后还需进一步推理"创建该记录的 API 是哪个、需要什么参数、是否需要先创建其他前置实体"。该推理链跨越源码阅读（Service/Controller/Mapper 分层）、数据库现状查询、API 序列规划与参数构造等多个环节，且不同 sink 的条件千差万别（唯一键冲突、引用计数非零、外键缺失、状态机未终结、用户锁定态……）。需要设计一种工具集与提示词框架，使 LLM Agent 能够自主完成这一语义推理。

**研究问题三：如何利用执行结果的偏差反馈让 Agent 在失败时自我修正？** Agent 的第一次尝试往往不会成功（参数错误、前置缺失、走到了其他分支）。需要将应用日志、HTTP 响应、数据库状态变化作为"偏差反馈"回传给 Agent，使其能够判断"走到了哪个分支、为什么没命中 sink、缺什么条件"，并据此修正下一步动作，直至命中或正确判定不可达。

### 2.3 研究目标

本课题的总体目标是：构建一个"静态 sink 定位 → LLM Agent 多步骤自动利用 → 日志命中验证"的端到端日志注入攻击构造框架，并在真实开源微服务系统上系统性验证其有效性。具体目标分解为：

（1）**构建日志 sink 的自动提取与分类方法**：对真实项目源码自动提取全部日志打印点，利用 LLM 分类其黑盒可达性，量化"多大比例的日志注入点无法被黑盒 fuzz 覆盖"，从而论证本方法的研究价值与目标池。

（2）**设计并实现基于工具增强的 LLM Agent 框架**：Agent 配备源码阅读、代码搜索、只读数据库查询、Redis 操作、HTTP 请求、日志读取等工具，在仅给定 sink 位置（甚至不给部署信息）的条件下自主完成前置条件构造与攻击触发。

（3）**建立基于日志标记的确定性命中判定**：Agent 的请求参数中植入攻击标记，以目标服务日志中出现该标记作为命中判据（harness 判定），对比基线计数，杜绝 Agent 自述命中带来的虚报。

（4）**在多个真实系统上系统性验证**：在 RuoYi-Cloud-Plus、pig 等真实开源微服务上对目标池中的 sink 进行批量验证，覆盖单跳业务、流程引擎状态机、跨服务调用、多租户隔离、客户端加密协议、服务端验证码等多类难点场景，并开展黑盒对照与提示公平性实验。

## 三、研究方案

### 3.1 整体方案

整体方案分为两个阶段，与开题报告的两阶段框架一脉相承，但各阶段内涵按新课题重新定义：

**阶段一：Sink 定位与目标池构建（静态分析）。** 给定 Java 微服务项目源码，自动化提取全部日志打印语句作为候选 sink。对每个 sink 输出：精确位置（类名/方法名/行号）、日志模板与参数表达式、语义类型（直接日志调用、全局异常处理器、AOP 切面等）。随后利用 LLM 对每个 sink 进行黑盒可达性分类：分析其日志分支的触发条件是否依赖数据库状态、内部异常、下游服务返回等黑盒无法控制的因素，输出分类标签与理由。分类结果构成两个池：黑盒可 fuzz 池（作为对照组）与目标池（黑盒不可 fuzz，作为本方法的目标）。同时，通过 Joern 调用图分析与 MyBatis XML/注解解析构建"HTTP API → 读写数据表"的映射目录，作为 Agent 的辅助工具。

**阶段二：LLM Agent 多步骤利用（动态验证）。** 对目标池中的每个 sink，启动一个工具增强的 LLM Agent，任务描述仅包含 sink 的源码位置与日志模板（标准模式下附加部署环境事实；黑盒对照模式下连部署信息也不提供）。Agent 循环执行：读源码理解 sink 分支条件 → 查询数据库/缓存诊断缺失的前置状态 → 规划并调用业务 API 构造前置数据 → 发送触发请求 → 读取应用日志判断是否命中 → 未命中则依据偏差修正后重试。命中判定由外部 harness 完成（日志标记基线增量），不信任 Agent 自述。

### 3.2 Agent 工具集设计

Agent 配备八类工具，覆盖"理解—诊断—构造—触发—验证"全链路：

| 工具 | 作用 |
|---|---|
| read_source | 读取项目源码片段，理解 sink 逻辑、条件分支与数据流 |
| search_code | 源码正则搜索，定位 Mapper XML、常量定义、过滤器等相关类 |
| query_db | 只读 SQL，查询表结构与现有数据，诊断缺失的前置状态 |
| redis_cmd | Redis 命令，检查/读取缓存状态 |
| read_logs | 读取目标服务日志，获取执行路径偏差反馈 |
| send_http | 发送 HTTP 请求（前置 API 调用 + 最终触发请求） |
| docker_ps | 列出运行中容器，定位目标服务与中间件 |
| get_api_catalog | 查询静态分析得到的"API → 读写表"目录 |

工具层做了若干**客户端正确性修复**（与 Agent 策略能力无关，保证实验公平性）：Content-Type 规范化、不可见字符转义（保证长 token 忠实复制）、登录 token 的会话自愈（LLM 转录长 JWT 偶发丢字符导致的 401 自动重试）、目标系统客户端加密协议的自动适配（如 pig 框架的密码 AES 加密传输）。

### 3.3 Agent 提示词与公平性控制

系统提示词为通用工作流（读源码→查库诊断→API 构造→触发→日志验证→偏差修正），不含任何特定 sink 的攻击知识。任务描述按三级提示粒度控制信息量：**none**（仅 sink 源码位置，纯黑盒对照）、**hint**（sink + API 入口 + 部署环境事实，标准灰盒模式）、**full**（调试用）。提示内容经过公平性审计：仅允许包含"可观测的部署事实"（登录端点、端口、容器名——测试者用 curl 即可探明），严禁包含"攻击策略"（前置数据构造方法、验证码绕过链等需要推理的内容）。审计中发现泄漏的任务全部降级重跑，最终作为证据的命中运行均不含攻击策略提示。

### 3.4 验证方法

命中判定采用**日志标记基线增量法**：Agent 的请求参数中植入攻击标记字符串，运行开始前统计目标日志中标记的出现次数作为基线，运行结束后重新统计，出现增量即判定命中。该判定不信任 Agent 的自述，且天然确定性（日志文件内容可精确 grep），无 SQL 盲注式验证的误报问题。

## 四、工作特色及难点

### 4.1 研究难点

**难点一：日志 sink 触发条件的语义多样性。** 与 SQL 注入 sink 的固定形态不同，日志分支的触发条件千差万别。我们在实验中遇到并解决的类型包括：唯一键冲突（需先造出同键记录）、引用保护（需先产生关联业务记录）、状态机未终结（需按顺序办理全部流程节点）、多租户隔离（需理解租户过滤对查询的影响）、用户状态门控（锁定/过期标志）、外部系统校验（验证码、客户端加密）。每一类都需要 Agent 将源码中的 if 条件翻译为"数据库/缓存/用户状态需要满足什么"，再翻译为"哪些 API 按什么顺序调用"。这一翻译链没有固定模板，是对 LLM 语义推理能力的真实考验。

**难点二：多步骤攻击链的自主编排与错误恢复。** 真实场景中前置构造往往需要 3~5 步 API 调用，且存在隐藏依赖（如创建租户前必须先有租户套餐、发起流程前必须先有业务单据记录）。这些依赖在源码中分散于多层调用链，Agent 必须在失败后利用日志堆栈、HTTP 响应码等偏差信号回溯定位缺失环节。如何让偏差反馈信息密度足够高、又不至于淹没 LLM 的上下文，是提示词与工具返回值设计的关键权衡。

**难点三：LLM 作为执行器的可靠性问题。** LLM 存在长字符串转录不稳定（我们实测 432 字符 JWT 转录丢失 4 字符导致 401）、单次推理波动（同一任务多次运行结果不一致）、上下文预算约束等固有缺陷。框架需要在工具层消化这些缺陷（如会话自愈），同时通过外部 harness 判定杜绝 Agent 虚报，并通过多次运行评估成功率稳定性。

**难点四：实验公平性控制。** "让 LLM 自主推理"的核心主张要求严格排除提示中的答案泄漏。区分"部署事实"（可观测、可试探，允许提供）与"攻击策略"（需要推理，禁止提供）的边界在实践中并不总是显然的，我们为此建立了提示审计流程，并对所有作为证据的运行保证零策略提示。

### 4.2 工作特色与创新点

**（1）首次系统量化"黑盒不可 fuzz"日志 sink 的比例，并以其为目标池。** 我们对 20 余个真实开源微服务项目的 2230 个日志打印点进行 LLM 分类，发现其中 1277 个 HTTP 可达，而可达部分中 84.7% 黑盒无法 fuzz（依赖内部异常 31.7%、数据库状态 17.6%、下游服务 14.2% 等）。这一量化结果直接论证了现有黑盒 fuzz 方案（如 AIOpsDoom）的覆盖盲区，也构成本方法目标池的来源。

**（2）提出"API-only 状态构造"约束下的 LLM Agent 多步骤利用范式。** 与直接修改数据库的方案不同，本方法要求 Agent 通过业务 API 完成全部状态构造，这与真实攻击者的能力边界一致，使验证成功的攻击链具有真实的可复现性。实验中 Agent 自主演出了多类超出预设的多步攻击链，例如：将攻击标记写入流程定义的 flowCode，经跨服务 dubbo 调用在租户同步日志中带出（标记随业务数据流动而非直接注入日志参数）；在删除路径被引用保护封死后，利用编辑接口修改定义的租户字段，借多租户查询隔离制造"逻辑孤儿"实例；注册带有攻击标记的用户名，经管理员锁定后在内省日志中带出标记（多用户状态编排）。这些链路均无任何提示先验。

**（3）以日志标记基线增量为判定的确定性验证闭环。** 不同于 SQL 盲注的时延/布尔推断，日志注入的命中验证是确定性的，本方法将其工程化为 harness 基线增量判定，使整套方法可以无人值守批量运行。

**（4）提示公平性审计方法。** 提出"部署事实 vs 攻击策略"的提示分级准则并落实为审计-降级-重跑流程，为 LLM Agent 类安全研究的实验可信性提供了可复用的方法论。

## 五、当前进展

### 5.1 已完成的工作

**（1）Sink 提取与分类管线（阶段一）已完成。** 覆盖 20 余个开源微服务项目，提取 2230 个日志 sink；LLM 逐条分类后得到：HTTP 可达 1277（57.3%）、不可达 937（42.0%）；可达部分中黑盒可 fuzz 仅 196（15.3%），**黑盒不可 fuzz 1081（84.7%）**，其依赖原因分布为：内部异常路径 405（31.7%）、数据库状态 225（17.6%）、下游服务依赖 181（14.2%）、打印值不可控 108（8.5%）、配置开关 107（8.4%）、缓存状态 55（4.3%）。该结果一方面量化了黑盒方案的盲区，另一方面给出了本方法目标池与后续研究（异常路径、下游 mock）的优先级依据。

**（2）Agent 框架与多项目验证环境已建成。** 基于 OpenAI 兼容接口 + 工具调用实现了 SinkAgent；完成 RuoYi-Cloud-Plus（含此前缺失的 workflow 模块，排障解决了 dubbo 注册中心被环境变量覆盖、nacos 配置坏字节等问题）与 pig-boot 单体的部署；构建了 Joern 调用图 + MyBatis 解析的 API→表映射目录。

**（3）16 次运行、14 次命中，13 个不同 sink 全部验证可自主触发。** 覆盖三类应用（RuoYi-Cloud-Plus、pig）与六类难点场景：

| 场景类型 | 代表性 sink | 成本（调用/秒） | Agent 自主完成的关键步骤 |
|---|---|---|---|

（4）**对照与公平性实验已完成。** 黑盒对照（不给 API/环境提示）：同 sink 成本由 26 调用/286s 升至 72 调用/682s，仍能命中，多出的 46 次调用全部用于基础设施探索——证明方法是能力而非提示先验，环境提示是 2.4× 的效率优化。提示公平性审计：发现并降级了 3 个存在策略泄漏的任务，降级重跑后 2 个命中、1 个差一步（预算耗尽于 multipart 编码细节，其核心策略已在无泄漏运行中验证）。

（5）**偏差反馈机制的有效性有了量化证据。** 统计显示：命中运行的"请求→日志检查"反馈环密度显著高于失败运行（如同一任务三次运行中，成功那次 read_logs 9 次且每次请求后核对分支，失败两次仅 2 次且盲目重发 21 次请求）；典型修正链显示一次 500 错误可引发 24 次调用的定向排查（读日志堆栈→顺链读源码→发现隐藏业务依赖→修正后命中），证明"执行路径偏差反馈"提供了模型从源码静态无法获得的运行时信息。

## 六、未来展望

**（1）扩大 db_state 验证规模。** 目标池中 db_state 类剩余 209 条，其中 yudao 项目 117 条为最大连片（其 pay 模块单模块即有 49 条），计划完成 yudao 环境部署后批量验证；pig 剩余条目中微信/钉钉/小程序登录系需要外部凭证服务，计划以 mock 服务补齐。

**（3）remote_service 依赖的 mock 环境。** 目标池中 181 条依赖下游服务返回值，计划通过 Docker 网络将下游服务替换为可控 mock，使 Agent 能控制返回内容触发日志分支。

**（5）成功率稳定性与成本分析。** 对已完成 sink 进行多轮重复实验，统计同配置下的成功率波动与成本分布；分析 LLM 转录缺陷等基础设施因素对成功率的影响及其工具层消化方案的效果；整理 FAIL 案例的归因分类（模型推理波动 vs 基础设施缺陷 vs 预算不足）。
