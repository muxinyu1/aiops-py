# 1. 选题背景及其意义

## 1.1 从 SQL 注入到 AIOps 遥测注入：威胁模型的演进

随着全球数字化转型的全面深化，Web 应用程序已演变成为支撑现代商业运营与核心业务逻辑的中枢。在云计算与微服务架构的推动下，现代 Web 系统的攻击面随 API 接口的爆炸式增长而持续扩大——Akamai《2026 年互联网状态报告》显示 API 请求已占全球 Web 流量的 80% 以上，而针对 API 业务逻辑的攻击在过去一年激增 113%。与此同时，软件系统的安全防线正在出现一种全新的、由 AI 自身引入的薄弱环节。

随着软件系统日益复杂，越来越多的组织将 AI 引入 IT 运维（AIOps），用 LLM 驱动的自主 Agent 自动化完成异常检测、根因分析与故障修复。这些 Agent 的工作方式是：接收系统产生的遥测数据（日志、指标、追踪），分析问题根因，然后建议或直接执行修复操作。USENIX Security 2026 收录的工作《When AIOps Become AI Oops》首次对这一模式进行了系统性安全分析，其核心发现是：**攻击者可以通过操纵系统遥测数据来误导 AIOps Agent，使其执行危害系统安全的操作**——例如将软件降级到含已知漏洞的版本、添加恶意软件源。

这类攻击的关键在于第一步：**攻击者如何将精心构造的载荷写入系统遥测数据（主要是日志）**。该工作给出的答案是其攻击工具 AIOpsDoom：枚举目标应用的所有 HTTP 端点，系统性地篡改每个请求中可修改的字段（URL 参数、POST 数据、HTTP 头部、Cookie 等）为攻击载荷，利用"应用记录错误日志时通常会将用户输入一并记录"这一普遍行为，使载荷自然进入日志。

## 1.2 黑盒 fuzz 的结构性盲区：本课题的出发点

AIOpsDoom 的黑盒 fuzz 方式有效，但本质上是"碰运气"——攻击者不知道哪些参数会落入日志、以什么格式落入、落入哪个服务的日志。我们对 20 余个真实开源 Java 微服务项目的实证分析表明，这种盲目性造成的是**结构性盲区而非偶然遗漏**：

对从项目源码中提取的 2230 个日志打印点（sink）逐一经 LLM 分类，其中 1277 个（57.3%）可经 HTTP 请求触达；而这 1277 个可触达的 sink 中，**黑盒 fuzz 可以触发的仅 196 个（15.3%），其余 1081 个（84.7%）在黑盒模式下结构上无法触达**。其不可达原因分布为：依赖内部异常路径 405（31.7%）、依赖数据库状态 225（17.6%）、依赖下游服务返回 181（14.2%）、打印值非请求可控 108（8.5%）、依赖配置开关 107（8.4%）、依赖缓存状态 55（4.3%）。

以一个典型例子说明：某菜单管理服务的日志分支为"当且仅当数据库中已存在与请求参数同路径的菜单记录时，打印路由冲突警告日志（其中包含请求参数）"。纯黑盒 fuzz 无论怎么变异请求参数，都只会得到 200 响应——除非先通过业务 API 在数据库中创建一条具有相同路径的种子记录。而这只是最简单的一类；实验中我们还遇到流程引擎状态机类（需按序办理全部流程节点）、多租户隔离类（需理解租户过滤对查询的影响）、用户状态门控类（需先注册再锁定特定用户）等远为复杂的前置条件。

**这类"多步骤前置状态构造"正是大语言模型 Agent 语义推理能力的用武之地**，也是本课题的核心主张：与其让 fuzzer 盲目变异，不如让 LLM Agent 阅读源码、理解日志分支的触发条件、诊断当前数据库/缓存状态、规划并执行一系列业务 API 调用，将系统状态"推送"到满足日志分支的位置，从而完成黑盒方法结构上无法完成的注入。

## 1.3 课题调整的缘由

开题阶段的课题"基于大模型的 Web SQL 注入漏洞验证方法研究"以 SQL 注入为对象，技术路线为：静态代码切片提供上下文 → LLM 语义变异生成 Payload → 执行流偏差反馈制导变异 → 带外 Oracle 确认。中期阶段经与导师讨论，将研究对象调整为遥测（日志）注入，主要基于两点考虑：

**其一，研究对象由"SQL 注入漏洞"演进为"AIOps 遥测注入"这一新兴威胁**（见 1.1 节），攻击的最终受害者从数据库变为 AI Agent 自身，威胁模型更新颖且具有前瞻性；同时 SQL 注入场景中"验证存在误报"的问题（开题报告研究问题之三）在日志注入场景下天然消失——日志文件中攻击标记的出现是确定性的命中证据。

**其二，原开题的技术组件在新的对象下全部保留且落点更清晰**：静态分析的对象从"SQL 注入 sink"变为"日志 sink"（且后者不是固定 API，sink 定位本身成为需要研究的问题）；LLM 的角色从"变异 Payload"升级为"多步骤攻击链的自主编排"；执行流偏差反馈从"细粒度插桩比较"落地为"应用日志+响应+DB 状态的运行时偏差"，且实验已证明其有效性（见研究进展）。

调整后课题名称为：**基于大语言模型智能体的 Web 应用日志注入漏洞多步骤利用方法研究**。

## 1.4 研究意义

本课题的意义体现在攻击与防御两侧。**攻击侧**：系统性构造出黑盒方法无法触达的日志注入路径，全面揭示 AIOps 遥测注入的真实威胁面——尤其是一阶防御（如 AIOpsShield 的抽象占位符清洗）无法覆盖的**二阶（存储型）注入路径**：攻击载荷先经业务 API 存入数据库，后续业务流程读取该数据时才落入日志，此类路径在 fuzz 阶段标记不会立即出现，是现有防御的结构性盲区。**防御侧**：sink 分析的结果可直接指导遥测清洗——哪些日志字段必须抽象化处理；同时"多步骤利用能否成功"的判定结果也为 AIOps Agent 的输入可信性评估提供了依据。**方法论侧**：本课题提出"部署事实 vs 攻击策略"的提示分级准则与审计-降级-重跑流程，为 LLM Agent 类安全研究的实验可信性提供了可复用的评价方法。

# 2. 国内外研究动态

本章按"攻击对象—攻击方法—大模型 Agent"三条线综述与本课题直接相关的工作；Web 安全与 SQL 注入的通用研究现状（静态污点分析、黑盒/灰盒 fuzz、验证通道）已在开题报告中综述，此处不重复。

## 2.1 AIOps 遥测注入攻击与防御

《When AIOps Become AI Oops》（USENIX Security 2026）是本课题最直接的先行工作。其攻击工具 AIOpsDoom 的流程为：爬虫枚举目标应用的所有 HTTP 端点 → fuzzer 将各请求字段替换为载荷 → 触发错误使载荷进入日志 → AIOps Agent 读取日志被误导。其局限在于攻击的触发完全依赖"载荷恰好出现在错误日志中"的运气。

该工作同时提出防御机制 AIOpsShield：在遥测数据到达 AI Agent 之前，将所有可能被攻击者控制的内容替换为无害的抽象占位符（如将具体用户名替换为 `<user>`）。其有效性依赖于一个假设——用户输入的具体内容对根因分析价值有限，抽象替换不影响 Agent 正常工作。

我们的实证分析指出二者的共同盲区：**占目标池 84.7% 的注入点无法靠盲目的请求变异触达**，因为它们的日志分支需要特定的数据库状态、内部异常或下游服务响应作为前置条件。这意味着 AIOpsDoom 会系统性遗漏这类注入路径，AIOpsShield 也不会为它们生成清洗模板——而一条真正危险的攻击路径完全可以藏在其中。这一盲区构成本课题的攻击面。

## 2.2 二阶（存储型）注入与污点分析

二阶注入指攻击载荷不立即生效，而是先经业务流程持久化（存入数据库），在后续业务流程读取该数据并使用时才触发的注入方式。存储型 XSS 与二阶 SQL 注入是其中被充分研究的两类，污点分析是处理此类问题的成熟技术：将 HTTP 入参标记为 Source，将敏感操作标记为 Sink，追踪污点数据穿越数据库等持久化存储的传播路径。

本课题将这一视角引入遥测注入：Source 是 HTTP 请求参数，Sink 是日志打印点（由项目实现决定，而非固定 API）。特别地，"SQL 注入的 sink"与"日志 sink"的本质区别在于后者没有固定 API 列表——任何 `log.info/warn/error` 调用、全局异常处理器、AOP 切面都可能成为 sink，且是否构成威胁取决于其参数是否用户可控、日志是否会被 AI Agent 读取。因此 sink 的自动发现与语义分类本身成为需要研究的问题（对应研究内容 3.2 节的问题一）。

## 2.3 LLM Agent 在安全领域的应用与局限

自 2023 年以来，LLM Agent 被引入漏洞挖掘的多个环节：PentestGPT 等工作将 LLM 用于渗透测试任务分解；已有工作尝试以 LLM 生成 Payload 或分析代码切片。但这些方案多为单轮生成，或仅依赖粗粒度的报错信息进行反馈，未将"多步骤业务操作序列的自主编排"作为一等公民。

与本课题最相关的是将 LLM 用于 REST API 规格推断的工作（Speculate, FSE 2026），其证明了 LLM 可以从源码推断 API 行为——这支持了我们"API→数据库表映射可由静态分析与 LLM 结合获得"的技术选型。同时，Agent 类方法的实验可信性问题（提示泄漏导致的能力虚高）在通用 Agent 评测中已被关注，但在安全攻击构造场景尚无系统性的处理准则，本课题的提示审计流程（见 4.2 节）填补了这一空缺。

综上：先行工作或证明了威胁存在但攻击手段盲目（AIOpsDoom），或提供了防御但存在二阶盲区（AIOpsShield），或证明了 LLM 具备代码语义推理的潜力（Speculate）但未用于多步骤攻击编排。**将三者结合——用 LLM Agent 的语义推理完成黑盒方法无法完成的多步骤日志注入——是本课题的定位。**

# 3. 课题研究内容

## 3.1 研究范围

本课题研究面向 Java 微服务 Web 应用的日志注入漏洞自动化利用技术。研究对象分为两个层面：

**静态层面是目标应用的源码与数据库模式。** 从真实开源微服务项目源码中提取日志打印语句作为候选 sink（按语义分类：直接日志调用、全局异常处理器、AOP 切面等），并结合调用图与 MyBatis ORM 映射推导"哪些 HTTP API 会读写哪些数据库表"。

**动态层面是可部署运行的微服务系统与其运行时状态。** 包括应用容器、MySQL、Redis 等中间件，以及这些组件中的业务数据状态（数据库表内容、缓存键值、用户账号状态等）。本课题的核心观察是：日志打印语句的可达性往往由运行时数据状态决定——例如"当且仅当数据库中存在某条与请求参数冲突的记录时，冲突日志分支才会执行"。

本课题假设攻击者具备目标系统的白盒源码访问权限（模拟供应链场景或内部攻击者，这也是揭示 AIOpsShield 类防御盲区所需的前提），可以部署并观察目标系统，但**不拥有数据库的直接写权限**——所有对系统状态的修改必须通过应用的业务 API 完成。这一约束是本方法区别于既有工作（如直接 INSERT 种子数据）的关键设定，它保证了"多步骤利用"是攻击者在真实场景中真正可以复现的。本课题不考虑拒绝服务、侧信道等攻击类型，仅关注通过 HTTP 请求触发的日志注入路径。

## 3.2 研究问题

本课题围绕"如何让 LLM Agent 自主完成从 sink 定位到多步骤攻击触发的全流程"这一中心，需要解决三个核心研究问题：

**研究问题一：如何系统化地定位日志 sink 并刻画其触发条件？** 日志打印语句在真实项目中数量庞大（我们在 20 余个开源微服务项目中共提取 2230 条），且是否构成安全威胁需要语义判断（哪些日志的参数是用户可控的、哪些日志会被 AIOps Agent 读取）。需要一种自动化的 sink 提取与分类方法，输出每个 sink 的精确位置、日志模板、参数表达式，并判定其"黑盒可 fuzz 性"——即纯随机 fuzz 是否可能触发，从而将无法黑盒触达的 sink 筛选出来作为 LLM Agent 的目标池。

**研究问题二：如何让 LLM Agent 从 sink 的源码语义推理出完整的数据库状态前置条件与对应的 API 序列？** 这是本课题最核心的问题。典型场景是：sink 的日志分支要求"数据库中存在 path 与请求参数相同的菜单记录"——纯黑盒测试不知道这一条件，而知道条件后还需进一步推理"创建该记录的 API 是哪个、需要什么参数、是否需要先创建其他前置实体"。该推理链跨越源码阅读（Service/Controller/Mapper 分层）、数据库现状查询、API 序列规划与参数构造等多个环节，且不同 sink 的条件千差万别（唯一键冲突、引用计数非零、外键缺失、状态机未终结、用户锁定态……）。需要设计一种工具集与提示词框架，使 LLM Agent 能够自主完成这一语义推理。

**研究问题三：如何利用执行结果的偏差反馈让 Agent 在失败时自我修正？** Agent 的第一次尝试往往不会成功（参数错误、前置缺失、走到了其他分支）。需要将应用日志、HTTP 响应、数据库状态变化作为"偏差反馈"回传给 Agent，使其能够判断"走到了哪个分支、为什么没命中 sink、缺什么条件"，并据此修正下一步动作，直至命中或正确判定不可达。

## 3.3 研究目标

本课题的总体目标是：构建一个"静态 sink 定位 → LLM Agent 多步骤自动利用 → 日志命中验证"的端到端日志注入攻击构造框架，并在真实开源微服务系统上系统性验证其有效性。具体目标分解为：

（1）**构建日志 sink 的自动提取与分类方法**：对真实项目源码自动提取全部日志打印点，利用 LLM 分类其黑盒可达性，量化"多大比例的日志注入点无法被黑盒 fuzz 覆盖"，从而论证本方法的研究价值并形成目标池。

（2）**设计并实现基于工具增强的 LLM Agent 框架**：Agent 配备源码阅读、代码搜索、只读数据库查询、Redis 操作、HTTP 请求、日志读取等工具，在仅给定 sink 位置（甚至不给部署信息）的条件下自主完成前置条件构造与攻击触发。

（3）**建立基于日志标记的确定性命中判定**：Agent 的请求参数中植入攻击标记，以目标服务日志中出现该标记作为命中判据（harness 判定），对比基线计数，杜绝 Agent 自述命中带来的虚报。

（4）**在多个真实系统上系统性验证**：在 RuoYi-Cloud-Plus、pig 等真实开源微服务上对目标池中的 sink 进行批量验证，覆盖单跳业务、流程引擎状态机、跨服务调用、多租户隔离、客户端加密协议、服务端验证码等多类难点场景，并开展黑盒对照与提示公平性实验。

# 4. 研究进展

本章重点展开。4.1 节介绍阶段一（sink 定位与目标池）的完成情况，4.2~4.3 节介绍阶段二（Agent 框架与验证）的设计与实现，4.4 节给出实验结果与对照分析，4.5 节总结偏差反馈机制的量化证据，4.6 节为中期节点完成度对照。

## 4.1 阶段一：Sink 提取与黑盒可达性分类（已完成）

**Sink 提取。** 针对覆盖 20 余个真实开源 Java 微服务项目的代码库，以日志调用 API（log.info/warn/error/debug 等）与全局异常处理器为模式，自动提取全部日志打印语句。每个 sink 记录：精确位置（项目/类名/方法名/行号）、日志级别、日志模板、各占位参数的表达式（如 `dbPath`、`e.getMessage()`、`instance.getId()`）。

**LLM 黑盒可达性分类。** 对 2230 个 sink 逐一经 LLM 分析其日志分支的触发条件，输出分类标签与理由。分类结果：

| 层级 | 数量 | 占比 |
|---|---|---|
| 全量提取 | 2230 | — |
| HTTP 可达 | 1277 | 57.3% |
| HTTP 不可达（定时任务、框架内部） | 937 | 42.0% |
| **HTTP 可达中：黑盒可 fuzz（对照池）** | **196** | 15.3% |
| **HTTP 可达中：黑盒不可 fuzz（目标池）** | **1081** | **84.7%** |

目标池 1081 个 sink 的黑盒不可达原因分布：

| 原因 | 数量 | 占可达比例 |
|---|---|---|
| exception_path 依赖内部异常 | 405 | 31.7% |
| db_state 依赖数据库状态 | 225 | 17.6% |
| remote_service 依赖下游服务 | 181 | 14.2% |
| printed_value_not_request 打印值不可控 | 108 | 8.5% |
| internal_state 依赖配置开关 | 107 | 8.4% |
| cache_state 依赖缓存状态 | 55 | 4.3% |

这一量化结果直接论证了 AIOpsDoom 类黑盒方案的结构性盲区（84.7% 的可达注入点无法靠请求变异触达），同时给出了本方法目标池以及后续研究（异常路径、下游 mock）的优先级排序。

## 4.2 阶段二：Agent 框架设计与实现

**Agent 循环。** 对目标池中的每个 sink，启动一个工具增强的 LLM Agent（模型 Qwen3.8-27B，OpenAI 兼容接口 + 原生工具调用）。任务描述仅包含 sink 的源码位置与日志模板（标准模式附加部署环境事实）。Agent 循环执行：读源码理解 sink 分支条件 → 查询数据库/缓存诊断缺失前置状态 → 规划并调用业务 API 构造前置数据 → 发送触发请求 → 读取应用日志判断是否命中 → 未命中则依据偏差修正后重试。

**工具集。** Agent 配备八类工具，覆盖"理解—诊断—构造—触发—验证"全链路：

| 工具 | 作用 |
|---|---|
| read_source | 读取项目源码片段，理解 sink 逻辑、条件分支与数据流 |
| search_code | 源码正则搜索，定位 Mapper XML、常量定义、过滤器等相关类 |
| query_db | 只读 SQL，查询表结构与现有数据，诊断缺失的前置状态 |
| redis_cmd | Redis 命令，检查/读取缓存状态 |
| read_logs | 读取目标服务日志，获取执行路径偏差反馈 |
| send_http | 发送 HTTP 请求（前置 API 调用 + 最终触发请求） |
| docker_ps | 列出运行中容器，定位目标服务与中间件 |
| get_api_catalog | 查询静态分析得到的"API → 读写表"目录（Joern 调用图 + MyBatis XML/注解解析构建） |

工具返回值经过截断与信息密度控制（保留堆栈、SQL、响应码等偏差信号，剔除冗余），保证单次调用不超过 LLM 上下文预算。

**工具层的客户端正确性修复。** 实验过程中发现并修复了多类 LLM 作为执行器的固有缺陷，修复均在工具层完成（不涉及 Agent 策略，保证公平性）：Content-Type 通配符规范化；不可见字符/NBSP 转义（保证长 token 忠实复制）；登录 token 会话自愈（LLM 转录 432 字符 JWT 偶发丢失字符导致 401，自动以最近登录 token 重试一次，实测修复后同任务从 81 调用失败转为 33 调用命中）；401 双风格判定（兼容"HTTP 401"与"HTTP 200 + body code:401"两种网关风格）；目标系统客户端加密协议自动适配（pig 框架要求登录密码以 AES/CFB 加密传输，密钥从字节码逆向还原后由工具层自动加密）。

**提示词与公平性控制。** 系统提示词为通用七步工作流（读源码→搜代码→查库诊断→API 构造→触发→日志验证→偏差修正），不含任何特定 sink 的攻击知识。任务描述按三级提示粒度控制：**none**（仅 sink 源码位置，纯黑盒对照）、**hint**（sink + API 入口 + 部署环境事实，标准灰盒模式）、**full**（调试用）。提示内容执行"部署事实 vs 攻击策略"分级准则：前者（登录端点、端口、容器名——测试者用 curl 即可探明）允许提供；后者（前置数据构造方法、验证码绕过链等需要推理的内容）严禁提供。审计中发现泄漏的 3 个任务全部降级重跑。

**命中判定（harness）。** Agent 的请求参数中植入攻击标记字符串 `<<SINK_REACHED>>`；运行开始前统计目标日志中标记出现次数为基线，结束后重新统计，出现增量即判定命中。判定不信任 Agent 自述，且天然确定性（日志可精确 grep），无 SQL 盲注式验证的误报问题。对应用侧 XSS 过滤器剥除尖括号的情况，判定放宽为标记子串匹配。

## 4.3 验证环境建设

完成了两类真实开源微服务系统的部署与验证环境构建：

**RuoYi-Cloud-Plus**（微服务架构，nacos 注册中心，8 个服务）：包括此前缺失的 workflow 模块从零部署——镜像构建推送、容器启动三轮排障（定位并修复了共享环境变量文件注入 `DUBBO_REGISTRY_ADDRESS=N/A` 导致 Dubbo 注册中心配置被覆盖、nacos 配置文件 UTF-8 坏字节两个深层问题）。**pig**（单体架构）：以启动参数覆盖凭证完成 pig-boot 单体部署，并从字节码逆向还原了其登录密码 AES/CFB 客户端加密协议（密钥 16 字节、无填充、base64 输出），由工具层自动适配。

## 4.4 实验结果

### 4.4.1 总体结果

截至目前累计 18 次运行、14 次命中，**13 个不同 sink 全部验证可由 Agent 自主触发**（4 次失败的归因见 4.4.4）。所有命中运行的日志中均出现完整或子串形式的攻击标记，由 harness 基线增量判定。

### 4.4.2 覆盖的难点场景与典型攻击链

13 个 sink 覆盖六类前置条件场景，每类给出代表性 sink、成本与 Agent 自主完成的攻击链：

| 场景类型 | 代表性 sink | 成本（调用/秒） | Agent 自主完成的关键步骤 |
|---|---|---|---|
| 单跳唯一键冲突 | 菜单路由冲突日志 ×3 | 26~53 / 286~968 | 读源码推条件→查库诊断→造种子→二次触发→日志确认→清理 |
| 数据库已存在异常 | MyBatis 异常处理器 | 62 / 887 | 任意唯一键表插入重复记录 |
| 流程引擎状态机 | 流程结束监听日志 | 104 / 904 | 建业务单据→发起流程→逐节点办理→监听器命中；失败后从报错偏差自学出业务依赖 |
| 跨服务调用链 | 租户同步日志 | 36 / 321 | 将标记写入流程定义 flowCode → 建套餐 → 建租户 → dubbo 同步将标记带入日志 |
| 多租户隔离绕过 | 流程定义未找到日志 | 86 / 1261 | 删除被引用保护封死后，利用编辑接口改定义租户字段制造逻辑孤儿 |
| 用户状态编排 | Token 内省锁定日志 | 100 / 558 | 注册带标记用户名→登录→锁定该用户→带 token 访问→内省拒绝命中 |
| 客户端加密+验证码 | 短信登录/手机号未注册日志 | 78~80 / 455~834 | 自主发现验证码答案存储于 Redis；以 STRLEN+GETRANGE 分段解码 JDK 序列化二进制读出答案；redis 密码字典盲试+配置文件交叉确认库号 |

三条攻击链值得单独说明，它们均**无任何攻击策略提示**，完全由 Agent 语义推理得出：

（1）**标记随业务数据流动**（跨服务链）：Agent 没有试图直接控制日志参数，而是将攻击标记写进流程定义的 flowCode 字段，随后创建租户触发 system 服务经 dubbo 调用 workflow 服务复制定义，标记随业务数据流动进入日志。这要求 Agent 理解"数据从哪个 API 进、经什么链路、从哪条日志出"的端到端流动。

（2）**多租户隔离绕过**（构造逻辑孤儿）：目标 sink 的条件是"删除流程实例时其定义查不到"。正常路径下定义被历史任务引用保护不可删——这本身就是另一条 sink。Agent 在删除被封死后，发现编辑接口没有引用校验，于是 PUT 修改定义的 tenantId 为不存在的租户，使实例查询定义时被租户隔离过滤掉，构造出"逻辑孤儿"。"让定义查不到"不一定非要删数据——这一洞察纯由推理得出。

（3）**多用户状态编排**（注册-锁定-内省）：目标 sink 要求"token 内省时用户处于锁定态"。Agent 意识到锁定当前用户会中断自己的攻击链，改为：注册用户名为攻击标记的新账号（注册接口与 DTO 字段均由读源码发现）→ 新账号登录获取 token → 用管理员权限锁定新账号 → 用新账号 token 访问受保护资源 → 内省检测到锁定态命中 sink。标记通过 username 字段贯穿注册、登录、内省三个环节。

### 4.4.3 黑盒对照与提示公平性

**黑盒对照**：对同一 sink 以 none 粒度（不给 API 入口与部署信息，仅给 sink 源码位置）重跑：成本从 26 调用/286s 升至 72 调用/682s，仍命中。多出的 46 次调用全部用于基础设施探索（猜测登录端点→遍历 nacos 开放 API 检索服务注册→试出网关与真实服务端口），核心的 sink 语义推理部分两种配置完全一致。结论：本方法是能力而非提示先验，环境提示的作用是效率优化（2.4×）而非能力开关。

**提示公平性审计**：对全部任务的提示执行"部署事实 vs 攻击策略"分级审计，发现 3 个任务存在策略泄漏（如将验证码绕过链写入提示），全部降级重跑：2 个降级后仍命中（其中短信验证码任务在无泄漏提示下，Agent 自主发现验证码答案存于 Redis 并以 STRLEN+GETRANGE 分段解码 JDK 序列化二进制读出答案），1 个差一步（预算耗尽于 multipart 编码细节，其核心攻击策略已在另一轮无泄漏运行中自主发现并验证）。**所有作为证据的命中运行均不含攻击策略提示。**

### 4.4.4 失败案例归因

4 次失败运行的归因：2 次源于 LLM 推理波动（同一任务重试即过，与提示词无关）；2 次源于基础设施缺陷（JWT 转录丢字符、401 判定风格未覆盖），修复工具层后重试均命中。无一次失败源于方法本身的推理能力缺失；另有一次零预置设定下的失败（Agent 无法凭空构造流程引擎的合法定义格式）促成了实验设定的修正——"环境中性基线数据预置 + 零攻击策略提示"，前者是任何真实部署都存在的可观测事实。

## 4.5 偏差反馈机制的量化证据

偏差反馈（执行路径 + 堆栈 + 日志分支）是 Agent 自我修正的信息来源，其有效性有正反两面量化证据：

**反馈环密度与成功正相关。** 对同一 sink（菜单根目录冲突）的三次运行对比：成功运行 read_logs 9 次，每次 HTTP 请求后核对日志确认实际走的分支；两次失败运行 read_logs 仅 2 次，在未核对分支的情况下盲目重发请求 21 次耗尽预算。

**典型修正链。** 流程状态机任务中，Agent 首次办理任务收到 500 错误后，连续读日志堆栈（3 次，逐步加大 tail 深度）→ 沿堆栈读取业务服务与过滤器源码（11 次）→ 发现"办理回调要求业务单据记录存在"这一隐藏前置 → 创建单据后重新发起并办理成功命中。该隐藏依赖在静态源码中位于 5 层调用链深处，无运行时堆栈指引几乎不可能发现——这正是"执行路径偏差反馈提供静态分析无法获得的运行时信息"的直接证据。

**工具异常的鲁棒性**：实验中还出现工具层偶发异常（部分 HTTP 错误响应导致变量未定义），Agent 均通过重试自行绕过，未影响命中——反馈循环对单点工具失败具备鲁棒性。

# 5. 工作特色及难点

## 5.1 研究难点

**难点一：日志 sink 触发条件的语义多样性。** 与 SQL 注入 sink 的固定形态不同，日志分支的触发条件千差万别。我们在实验中遇到并解决的类型包括：唯一键冲突（需先造出同键记录）、引用保护（需先产生关联业务记录）、状态机未终结（需按顺序办理全部流程节点）、多租户隔离（需理解租户过滤对查询的影响）、用户状态门控（锁定/过期标志）、外部系统校验（验证码、客户端加密）。每一类都需要 Agent 将源码中的 if 条件翻译为"数据库/缓存/用户状态需要满足什么"，再翻译为"哪些 API 按什么顺序调用"。这一翻译链没有固定模板，是对 LLM 语义推理能力的真实考验。

**难点二：多步骤攻击链的自主编排与错误恢复。** 真实场景中前置构造往往需要 3~5 步 API 调用，且存在隐藏依赖（如创建租户前必须先有租户套餐、发起流程前必须先有业务单据记录）。这些依赖在源码中分散于多层调用链，Agent 必须在失败后利用日志堆栈、HTTP 响应码等偏差信号回溯定位缺失环节。如何让偏差反馈信息密度足够高、又不至于淹没 LLM 的上下文，是提示词与工具返回值设计的关键权衡。

**难点三：LLM 作为执行器的可靠性问题。** LLM 存在长字符串转录不稳定（实测 432 字符 JWT 转录丢失 4 字符导致 401）、单次推理波动（同一任务多次运行结果不一致）、上下文预算约束等固有缺陷。框架需要在工具层消化这些缺陷（如会话自愈），同时通过外部 harness 判定杜绝 Agent 虚报，并通过多次运行评估成功率稳定性。

**难点四：实验公平性控制。** "让 LLM 自主推理"的核心主张要求严格排除提示中的答案泄漏。区分"部署事实"（可观测、可试探，允许提供）与"攻击策略"（需要推理，禁止提供）的边界在实践中并不总是显然的，我们为此建立了提示审计流程，并对所有作为证据的运行保证零策略提示。

## 5.2 工作特色

**特色一：攻击构造与运行时状态感知深度耦合。** 与既有 fuzz 方案将请求变异视为独立动作不同，本方法中每一次请求都是"状态机推进"——Agent 维护对系统状态（数据库行、缓存键、用户标志）的运行时认知，并据此选择下一步动作。实验中的多用户编排链（注册-登录-锁定-内省）体现了这种状态感知的深度。

**特色二：偏差反馈闭环覆盖多源信号。** 反馈不仅来自应用日志（执行到了哪个分支），还包括 HTTP 响应（405 提示方法错误、500 提示内部异常）、数据库状态变化（种子是否落库）、异常堆栈（指向缺失前置的类与方法）。多源信号的交叉使 Agent 能够区分"参数错"与"前置缺"两类本质不同的失败。

**特色三：确定性验证支撑无人值守批量运行。** 日志标记基线增量判定无歧义、可自动化，使整套方法可以对目标池批量执行而不需人工判定，这是从"单点验证"走向"规模化评估"的工程基础。

# 6. 当前成果和创新点

## 6.1 当前成果

**（1）实证量化了黑盒 fuzz 在日志注入场景的结构性盲区。** 对 20 余个开源微服务项目 2230 个日志 sink 的 LLM 分类表明：HTTP 可达 sink 中 84.7% 黑盒不可 fuzz，其根因分布（异常路径 31.7%、DB 状态 17.6%、下游服务 14.2% 等）为攻击面评估与防御模板生成提供了数据基础。

**（2）构建了端到端可运行的 LLM Agent 日志注入利用框架。** 包含 sink 提取分类管线、八工具 Agent、工具层健壮性修复、harness 基线增量判定，已对两类真实开源系统完成部署与批量验证运行。

**（3）13 个不同 sink 的多步骤攻击链全部自主构造成功**（16 次运行 14 次命中），覆盖单跳业务、流程引擎状态机、跨服务调用、多租户隔离、用户状态编排、客户端加密+验证码六类难点场景，且所有作为证据的运行均通过提示公平性审计（零攻击策略提示）。

**（4）形成了一套可复用的实验方法论**：提示分级准则（部署事实 vs 攻击策略）、审计-降级-重跑流程、失败归因分类（模型波动/基础设施/预算）、反馈环密度与成功率的关联分析。

## 6.2 创新点

**创新点一：首次系统量化"黑盒不可 fuzz"日志 sink 的比例并以其为目标池。** 已有工作（AIOpsDoom）证明了遥测注入威胁但未度量黑盒方法的覆盖盲区；本课题的分类管线给出了盲区的精确刻画（84.7%），并证明这些盲区可以被 LLM Agent 的语义推理覆盖。

**创新点二：提出"API-only 状态构造"约束下的多步骤利用范式。** 要求 Agent 通过业务 API（而非直接写库）完成全部前置状态构造，与真实攻击者能力边界一致。实验中 Agent 自主演示了三类超出预设的攻击形态：标记随业务数据流动（跨服务 dubbo 链）、利用多租户隔离构造逻辑孤儿、多用户注册-锁定编排——均为无提示先验的自主推理产物。

**创新点三：偏差反馈驱动的错误恢复机制及其量化评估。** 将应用日志堆栈、HTTP 响应、DB 状态变化作为多源偏差信号回传 Agent，量化证据表明反馈环密度与命中率正相关（成功运行 9 次日志核对 vs 失败运行 2 次），且单次 500 错误可引发 24 次调用的定向排查并最终发现 5 层调用链深处的隐藏前置——提供了静态分析无法获得的运行时信息。

**创新点四：LLM Agent 安全实验的公平性评价方法。** "部署事实 vs 攻击策略"提示分级准则与审计-降级-重跑流程，解决了 LLM Agent 类研究中"提示泄漏导致能力虚高"的可信性问题，可推广至同类研究。
